# MQTT コマンド受信チャネル設計仕様

**作成日**: 2026-06-20
**関連タスク**: 将来実装 — MQTT によるコマンド受信チャネル

## 背景・動機

### 現状の課題

複数の pipe が複数の viewer に分散している環境で、観測・制御の集約が弱い。

```
[各 Ubuntu pipe]   → viewer 1 (Tailscale 中央)
[Ubuntu PC pipe]   → viewer 2 (PC ローカル)  ← 統合したい
[Windows native]   → viewer 3 (Windows)      ← 観測のみで一本化したい
```

### MQTT が解決すること

viewer 1 に MQTT broker を置き、全 pipe のハブにする。

```
[各 Ubuntu pipe]   ←─MQTT─→ [viewer 1 / MQTT broker]  双方向
[Ubuntu PC pipe]   ←─MQTT─→ [viewer 1 / MQTT broker]  双方向 (viewer 2 を統合)
[Windows native]    ──MQTT──→ [viewer 1 / MQTT broker]  観測のみ
```

- viewer 1 の MQTT broker が Tailscale 上でどこからも到達可能
- Webhook が届くなら MQTT も届く（同じネットワーク経路）
- Ubuntu PC pipe が viewer 1 に統合され、viewer 2 が不要になる

## 役割分担の設計決定

**イベント配信（pipe → viewer）**: HTTP webhook のまま。変更なし。

**コマンド受信（viewer → pipe）**: MQTT のみ。

この分離により:
- HTTP webhook の設計を一切変えなくてよい
- `deliverToSubscriber` は HTTP のまま完結
- MQTT は config の別セクションに独立

## Config 設計

```json
{
  "mqtt": {
    "url": "mqtt://id:pass@viewer1:1883",
    "commandTopic": "claude/pipe-A/send"
  }
}
```

- `url`: MQTT broker への接続情報（認証情報含む）
- `commandTopic`: pipe がコマンドを受け取るトピック名

`subscribeTopic` / `publishTopic` の案（案A）も検討したが、「MQTT はコマンド受信のみ」と役割を絞ることでシンプルになった。

## Webhook ペイロードへの情報露出

viewer が pipe の状態を把握するために、全 webhook ペイロードに以下を含める（v0.8.3 実装済み）:

```json
{
  "communicationMode": "bidirectional",
  "mqttCommandTopic": "claude/pipe-A/send"
}
```

**セキュリティ上の注意**: `mqtt.url`（broker URL・認証情報）はペイロードに含めない。`commandTopic`（トピック名）のみ露出する。

## communicationMode の判定ロジック

```js
if (subscriberCount === 0) {
  communicationMode = 'watch-only';
} else if (callbackUrl || mqttCommandTopic) {
  communicationMode = 'bidirectional';
} else {
  communicationMode = 'webhook-only';
}
```

| 条件 | communicationMode |
|---|---|
| subscriber なし | `"watch-only"` |
| `callbackUrl` または `mqtt.commandTopic` あり | `"bidirectional"` |
| subscriber あり、どちらもなし | `"webhook-only"` |

## OS 別の動作

| pipe の OS | MQTT イベント送信 | MQTT コマンド受信 → claude -p |
|---|---|---|
| Linux / Mac / WSL | N/A（HTTP webhook） | ✓ 実装可能 |
| Windows native | N/A（HTTP webhook） | ✗ claude -p 非対応（node-pty 必要） |

Windows native は `mqtt` セクションを省略するか、設定しても `commandTopic` を subscribe しない扱いにする。

## 実装時の差し込みポイント

`src/subscribers.js` の `deliverToSubscriber`（旧: `postToSubscriber`）がプロトコル dispatch の起点になる予定:

```js
// 将来のイメージ（未実装）
function deliverToSubscriber(url, payload, authorization, label) {
  if (url.startsWith('mqtt://') || url.startsWith('mqtts://')) {
    return deliverViaMqtt(url, payload, label);  // MQTT publish
  }
  return deliverViaHttp(url, payload, authorization, label);  // 既存
}
```

ただし MQTT コマンド受信は subscriber ではなく `config.mqtt` セクションから別途 subscribe する構造なので、`deliverToSubscriber` とは独立したモジュール（例: `src/mqtt-receiver.js`）になる可能性が高い。

## 実装時に必要な検討事項

- **ライブラリ**: `mqtt` npm パッケージ（mqtt.js）
- **QoS レベル**: 0（fire and forget）か 1（at least once）か
- **コマンドのペイロード形式**: `{ prompt, projectPath, sessionId?, model? }` など Send API に近い形
- **MQTTS**: `mqtts://` スキームで自動 TLS。mqtt.js が対応済みなので設計上は単純
- **再接続**: broker 切断時の自動再接続ロジック
- **Windows native の扱い**: `commandTopic` が設定されていても claude -p を実行できないので、起動時に警告を出すか無視するか
