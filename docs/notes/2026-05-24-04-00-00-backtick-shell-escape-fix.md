# バッククォート・`$` のシェルエスケープ修正 - 開発記録

**作成日**: 2026-05-24
**関連タスク**: 長文 Markdown 送信時のバッククォート問題 / Mermaid 記法で生成されるゴミファイルの解消

## 問題

長文 Markdown を Send API で送信すると壊れることがあった。特に以下のケース：

- バッククォートを含むコードブロック（` ```mermaid ` など）が変なゴミファイル生成を伴って失敗
- `$HOME` などの `$` 始まり文字列が環境変数に展開される

## 原因

`src/sender.js` の `startNewSession` / `sendToSession` で `script -q -c <command>` にシェル文字列を渡す構造になっており、引数の引用処理が不十分だった。

```javascript
// 修正前
if (arg.includes(' ') || arg.includes('"') || arg.includes("'") || arg.includes('\n') || arg.includes('\r')) {
  return `"${arg.replace(/\\/g, '\\\\').replace(/"/g, '\\"')}"`;
}
return arg;
```

このロジックは以下の問題があった：

1. **判定条件にバッククォート・`$` が含まれない** → これらだけ含む引数はクォートされず素通り
2. **クォートされた場合のエスケープに `` ` `` / `$` が含まれない** → ダブルクォート内でも展開される

`script -c "command"` は内部で `/bin/sh -c "command"` を実行するため、シェルメタ文字は確実にエスケープが必要。

### Mermaid ゴミファイル生成のメカニズム

トリプルバッククォートを含むプロンプト（例: ` ```mermaid\ngraph TD\n  A-->B\n``` `）は、シェルがコマンド置換として解釈を試み、内部のテキストをコマンドとして実行しようとする。実行失敗の副作用でゴミファイルが残ることがあった。

## 試行錯誤

### アプローチA（採用）: 全引数を常時ダブルクォート＋4文字エスケープ

**試したこと**: 条件分岐を撤廃し、全引数を常にダブルクォートで囲んだ上で `\`、`"`、`` ` ``、`$` を漏れなくエスケープ

**結果**: 成功

**コード例**:
```javascript
const claudeCommand = `claude ${claudeArgs.map(arg =>
  `"${arg.replace(/\\/g, '\\\\').replace(/"/g, '\\"').replace(/`/g, '\\`').replace(/\$/g, '\\$')}"`
).join(' ')}`;
```

**置換順序の制約**: `\` → `"` → `` ` `` → `$` の順で行う必要がある。`\` を最初に置換しないと、後段の置換で追加された `\` を二重エスケープしてしまう。

---

### 検出されたイレギュラー: `-` 始まりプロンプト

エスケープを直しても、プロンプトが `- 1\n- 2\n- 3` のように `- ` で始まる場合は **Claude CLI 側で `error: unknown option` エラー** になる。

```
claude "-p" "- 1
- 2
- 3" "--output-format" ...
→ error: unknown option '- 1\n- 2\n- 3'
```

これは Claude CLI のパーサーが `- ` 始まりの値をフラグとして解釈しようとするため。`claude -p -- "- 1\n..."` のように `--` 区切りを入れれば回避できるが、引数の並びを根本的に変える必要があり、コード変更コストが大きい。

**判断**: 今回は修正しない。理由は3点：

1. エラーで弾かれて exit するだけで、汚染やゴミ生成はない（クリーンな失敗）
2. 実用上 `- ` 始まりプロンプトは極めて稀
3. 引数構築ロジックを大きく変える必要があり、本筋（エスケープ強化）から外れる

## 解決策

**実装場所**: `src/sender.js`（2箇所: `startNewSession`、`sendToSession`）

**主なポイント**:
1. 条件分岐を撤廃し全引数を必ずダブルクォートで囲む
2. ダブルクォート内でも展開される `` ` `` と `$` のエスケープを追加
3. 置換順序を `\` → `"` → `` ` `` → `$` に固定

## 検証

実セッション `e031b267-1288-485b-9df4-6493c7c8fcb0` で 26 メッセージ（ユーザー9 + アシスタント17）の苛烈な検証を実施。長文 Markdown（コードブロック・水平線・箇条書きを含む）が問題なく届くことを確認。

## 学び

- **シェルエスケープは「クォートするかどうか」より「クォート内で何を escape するか」が肝**。ダブルクォート内でも `` ` `` と `$` は展開されることを忘れがち
- **置換順序は重要**。`\` を最初に処理しないと多重エスケープになる
- **`script -c` は便利だが内部でシェル評価が走る**。PTY 用途でも完全には透過にならない
- **修正の境界線を引く判断**: 99% の症状を直す最小修正 vs 1% の残存イレギュラーまで直す大幅修正。今回は前者を選択

## 今後の改善案

- `-` 始まりプロンプト問題は別途検討（必要になったら `--` 区切り対応 or 別経路でプロンプト渡し）
- エスケープロジックの単体テスト追加（現状テストフレームワーク未導入）
